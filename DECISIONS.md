# Decisions

One-line rationale for every non-obvious choice.

- **Repo root is `/Users/manavshah/excelclone` (existing empty dir), not a nested `gridline/`** — the working directory was created for this project; nesting would add noise.
- **Rust installed via Homebrew `rustup` (keg-only) + stable toolchain** — no toolchain existed on the machine; rustup is required for wasm32 target management.
- **Version pinning via committed `Cargo.lock` + `package-lock.json` rather than `=x.y.z` in manifests** — lockfiles pin exact versions for every build (incl. transitive deps) while keeping manifests readable; CI uses the lockfiles.
- **Wasm crate named `gridline-wasm` (dir `crates/wasm`)** — crate name `wasm` would collide conceptually with the ecosystem; dir layout follows the spec.
- **`serde-wasm-bindgen` for JS↔Rust value passing** — boring, maintained, avoids JSON string round-trips where possible.
- **CI on `dtolnay/rust-toolchain` + `Swatinem/rust-cache`** — the standard boring GitHub Actions setup for Rust workspaces.
- **getrandom wasm_js backend cfg in `.cargo/config.toml` + target-specific getrandom dep in gridline-wasm** — ulid→rand→getrandom 0.3 requires an explicit JS entropy backend on wasm32-unknown-unknown.

## M1 — Engine core

- **`SheetId` (stable u32) as the internal sheet key; names resolved at the edges** — renames and reorders must not invalidate the dependency graph or cell keys.
- **Sheet names compare case-insensitively (Excel behavior)** — `Data` and `data` are the same sheet; `SheetAdd` rejects a case-variant duplicate.
- **Sheet rename rewrites formula text; sheet delete replaces refs with `#REF!`** — matches Excel; failing loudly beats silently dangling refs.
- **Unknown bare identifiers parse to a `#NAME?` literal node rather than a parse error** — named ranges arrive in P1; until then the cell must still accept the input and show `#NAME?` like Excel, not reject the edit.
- **`^` is left-associative and unary minus binds tighter than `^`** — matches Excel: `2^3^2 = 64`, `-2^2 = 4` (differs from most programming languages).
- **A multi-cell range in scalar context is `#VALUE!`; no implicit intersection** — implicit intersection (`@`) is P2 work; loud failure until then.
- **Aggregates distinguish references from direct arguments** — `=AVERAGE(A1)` with text in A1 is `#DIV/0!` (text behind a ref is ignored) while `=AVERAGE("x")` is `#VALUE!`; single-cell refs follow the range rule, matching Excel.
- **Cycles are detected structurally during recalc (Kahn's algorithm; unprocessed nodes are cyclic) and marked `#CIRC!`** — no iterative-calculation mode in v1; recalc always terminates.
- **A formula whose watched range covers its own cell (`A5 = SUM(A1:A10)`) is a cycle** — matches Excel.
- **Recalc order is deterministic (keys sorted at every tie-break)** — required for the replay invariant; two runs of the same log must produce identical results.
- **`now_ms` is injected into the engine rather than read from the system clock** — `NOW`/`TODAY` must be replayable from the event log.
- **Excel's 1900 leap-year quirk is NOT reproduced** — dates use a plain proleptic serial system; documented per spec §5. Revisit in the Parity Track if the oracle corpus demands it.
- **`ROUND` snaps within 1e-9 before rounding half-away-from-zero** — Excel rounds the *decimal* the user typed, so `ROUND(2.675,2)` is 2.68 even though the binary double is just below 2.675.

## M2 — Engine complete

**Date system**
- **Excel's phantom 1900-02-29 IS reproduced** (serials ≥ 61 use a 1899-12-30 epoch) — the spec permits skipping it, but every real workbook's dates would then be off by one against Excel. Serial 60 itself has no calendar date and converts to `#NUM!` rather than a fake 1900-02-29. *(Revisited in P1: see below.)*

**Structural operations**
- **Undo stores recorded previous state, not inverse actions** — cell-level ops record the cells they touched; ops that relocate cells wholesale (insert/delete row/col, sort, merge, sheet ops) record the affected sheets. Restoring returns the replaced state, so undo and redo are the same operation run in opposite directions, and both flow through `apply()` and emit events. A synthesized inverse *action* cannot express `#REF!` damage faithfully; recorded state can.
- **A copy tiles into a target that is an exact multiple of the source, else pastes once at the anchor** — matches Excel's common cases without implementing its full paste-shape dialog.
- **Cut/paste moves formulas verbatim and retargets references elsewhere that pointed into the moved block** — matches Excel. A range reference follows only when it lies *entirely* inside the moved block; partial overlaps are left alone, as in Excel.
- **Fill treats a single numeric seed as a copy, two or more as a linear series** (constant step, verified consistent). Excel uses a least-squares trend for longer selections; we use the constant step and fall back to repeating the block when no consistent progression exists.
- **Fill has no date awareness yet** — a lone date cell copies rather than incrementing by a day, because number formats (which is how Excel knows a number is a date) arrive in M5. Revisit then.
- **Sort shifts moved rows' relative formula references by the distance travelled** and places blanks last in both directions, matching Excel.
- **Filters are view state** (`Sheet::hidden_rows`), computed from a checkbox-style allowed-value set; no cell values change and no recalculation is triggered.
- **Committing an empty cell edit clears the cell** rather than storing an empty string, so `ISBLANK`/`COUNTBLANK` match Excel.

**Function semantics decided while implementing**
- **Lookups return `0` for a blank result cell** (`VLOOKUP`/`HLOOKUP`/`INDEX`/`XLOOKUP`), matching Excel; `CHOOSE` passes `Empty` through since it evaluates an expression rather than reading a grid.
- **`XLOOKUP` supports exact modes only** (`match_mode` 0 and 2); approximate and binary-search modes return `#VALUE!` until P2.
- **`INDEX` with a 0 index is honoured only when that dimension is a single row/column**; a whole-row/column array result needs the dynamic-array model (P2), so anything else is `#VALUE!`.
- **Approximate lookup is a linear "last entry ≤ lookup" scan, not a binary search** — degrades predictably on unsorted data instead of reproducing Excel's binary-search surprises. Pinned for the oracle corpus.
- **Criteria comparisons are type-restricted**: `">100"` matches only numbers, `"apple"` only text; `"<>"` is the one inclusive operator. Without this, Excel's cross-type ordering (text > number) would make `">100"` match `"zebra"`.
- **`RAND`/`RANDBETWEEN` derive from the injected clock via a pure SplitMix64 mixer, not system entropy** — the engine must stay replayable and I/O-free. Consequence: two `RAND()` calls with identical arguments in one recalc return the same value.
- **`COUNTIF` and friends propagate errors found anywhere in a scanned range**, where Excel ignores them. Pinned as an open oracle question for P0 rather than guessed at.
- **`numfmt` fails soft**: an unrecognised format code renders as General instead of erroring, because it only affects display.

## M2 — xlsx / csv I/O

- **Preservation is implemented by patching the original zip, not by regenerating it** — on import every part is retained verbatim; on export only each modelled sheet's `<sheetData>` (and `<mergeCells>`) is replaced, leaving `<cols>`, `<conditionalFormatting>`, `<dataValidations>`, `<pageMargins>`, tab colours, charts, pivot caches and VBA byte-identical. Per-cell style indices (`s=`) captured at import are written back, so formatting we do not model still survives.
- **Inline strings (`t="inlineStr"`) are used when rewriting sheet data** — writing shared strings would mean rewriting `sharedStrings.xml`, which is exactly the kind of shared part the preservation rule exists to protect.
- **New workbooks export via `rust_xlsxwriter`; imported ones via the zip-patch path** — the fixed choice in §4 covers the from-scratch case, and the preservation rule cannot be expressed through it.
- **Adding a sheet to an imported workbook fails loudly on export** rather than silently dropping it, because writing a new sheet part also means rewriting `workbook.xml` and its relationships. Known gap; the error names the sheet.
- **`_xlfn.` / `_xlws.` function prefixes are stripped at parse time** — xlsx stores every post-2007 function that way (`_xlfn.TEXTJOIN`, `_xlfn.XLOOKUP`, `_xlfn.IFS`, `_xlfn.CONCAT`) and Excel hides it. Without this, importing any modern real-world workbook produced `#NAME?`. Caught by the golden-workbook round trip, not by a unit test.
- **A formula whose source contains `_xlfn.` is re-rendered from its AST for display**, so the formula bar shows `=TEXTJOIN(...)` like Excel; all other formula text is stored exactly as written.
- **A formula our parser rejects imports as literal text plus a warning** — never silently dropped, and the original text survives the round trip.

## M4 — Event spine

- **The event envelope and privacy redaction live in `crates/engine/src/telemetry.rs`, not in the server or the client** — the client redacts by calling this same code compiled to wasm. A privacy guarantee implemented twice is a guarantee that will eventually be implemented differently, and the divergent copy is the one that leaks. It also keeps the engine I/O-free: these are pure data transforms.
- **A test asserts the code's action vocabulary appears in `docs/EVENTS.md`** — the transparency page renders that document, so an action captured but not documented would be undisclosed capture. That fails the build rather than shipping.
- **Salt and text are separated by a `0x1f` byte before hashing** — otherwise salt `"ab"` + value `"c"` would collide with salt `"a"` + value `"bc"`.
- **Sheet names, filter values and search terms are hashed under `structural`, not just cell values** — a sheet named "Payroll Q3" or a filter on an email address is user content by any reasonable reading of the promise in `docs/PRIVACY.md`.
- **Formulas are kept verbatim in `structural` mode** — their structure is the entire point of mining, and they describe shape rather than content. This is stated plainly in the consent copy rather than buried.
- **The server rejects an envelope claiming `full` privacy mode when the actor's consent is `structural`** — beyond the spec, but without it a buggy or forged client could smuggle verbatim values in under a structural grant, contradicting what the user was promised.
- **Sessions are derived server-side from `ts_ms` gaps rather than trusting the client's `session_id`** — the client's id is retained alongside so disagreements (reload, crash recovery, a tab left open over lunch) are visible rather than silent.
- **`ts_ms` is the client wall clock, deliberately** — a batch flushed hours later still sessionizes where the work actually happened. `received_at` is used only for export `since` filtering. Clock skew can therefore fabricate or hide a split; noted as a known limit.
- **Ingest is partially accepting: good events in a mixed batch are stored** and bad ones are reported with reasons. An all-or-nothing batch would let one malformed event discard a whole session's work.
- **Rejected actions stay in the replay log** — replay must reject exactly the same actions the live session did, so a log records attempts, not just successes.
- **`format_number_general` caps at 15 significant digits** — Excel's General format does, which is why `=0.1*3` shows `0.3` there. Printing the shortest round-trip float instead exposed IEEE noise on nearly every decimal a user sees.
- **`context.sheet` is redacted under `structural`, not just payload sheet names** — the context rides on every envelope, so leaving it in clear would have disclosed the sheet name on every event *and* handed an observer a matched hash/plaintext pair, unpicking every other hash made with that workbook's salt. Redacting a value in one field while sending it in clear in another is worse than not redacting it at all. Caught by an end-to-end test that renames a sheet to a sensitive string and asserts it never appears in transmitted bodies.
- **Redaction fails closed** — if the redactor throws, the client transmits an empty sheet name rather than the raw one.
- **The `actor_id` is stamped at flush time, not at capture time** — the server's identity arrives asynchronously, and anything buffered before it lands would otherwise carry the client's placeholder and be rejected as a mismatched actor. Since rejected events are retried unchanged, those events would have been lost permanently.

## M5 — Grid completeness

**Formatting model**

- **Formats live in a second sparse map on the sheet (`Sheet::formats`), not in `Cell`** — a format has to be able to exist without a value, because formatting a blank column before typing into it is an ordinary gesture. Putting the format inside `Cell` would mean inventing a cell to hold it, which then appears in the used range, in CSV export, and in every count of populated cells. It also keeps the evaluator, dependency graph and parser entirely unaware of presentation.
- **Formats are interned in a workbook-level append-only table (`FormatTable`)** — the same shape xlsx uses with `cellXfs`; a bold column costs one `CellFormat` and N `u32`s. Append-only means an id recorded for undo still resolves after any number of intervening changes, which is what lets `UndoState::Formats` record ids rather than whole formats. Interning is a linear scan because real workbooks have tens of distinct formats, and a `Vec` stays trivially serializable and deterministically ordered.
- **`Sheet::used_range` stays blind to formatting; `Sheet::painted_range` unions cells, formats and merges** — the used range is the *data* extent, which is what CSV export and whole-sheet ranges mean. A bold empty column is not data, but the grid still has to draw it.
- **The unit of change is a `FormatPatch` naming one attribute, and an action carries a list of them** — "make this bold" must not clear the fill colour set a moment ago. An `Option<Option<T>>` field would have had to distinguish "clear it" from "leave it alone" by JSON `null` versus a missing key, which serde does not do without a custom deserializer; `{"set":"fill_color","value":null}` is unambiguous.
- **The state snapshot records resolved formats, not format ids** — an id is an artefact of the order formats happened to be interned, which differs between two paths to the same workbook. That is exactly the difference the replay suite must not see.
- **Border presets are a range gesture, not a cell attribute** — `Outline` gives a cell different edges depending on where in the range it sits, so the preset is resolved per cell at apply time and only the resulting edges are stored.
- **Colours are normalized to `#rrggbb` at apply time** — otherwise `#FFF`, `#ffffff` and `FFFFFF` would intern as three distinct formats that render identically.
- **A formatting action is capped at `MAX_FORMAT_CELLS` (200k) and fails loudly above it** — we model formatting per cell, not per row/column as xlsx does, so "bold this whole column" would otherwise materialise a million map entries. Lifting the cap properly means row and column format defaults, which v1 does not have.
- **Formatting travels with contents through paste, cut, fill, sort and insert/delete, but not through paste-values** — "paste values" means the numbers without the dressing. Sorting a range narrower than the formatted region therefore leaves the outer columns' borders behind at their positions while the inner ones move with their rows; that is what Excel does too.
- **`Delete` clears contents and leaves formatting; `FormatClear` is a separate action** — Excel's semantics, and the reason "Clear Formats" is its own menu item.
- **Formatting never triggers a recalculation** — a number format changes how a value reads, not what it is.

**Find & replace**

- **`FindReplace` is one engine action, not N `CellEdit`s** — it undoes as a single step, emits one `find.replace` event for the miner, and cannot half-apply.
- **Matching and replacement both operate on the cell's formula-bar text, never its computed value** — there is no way to write a replacement back into a formula's result, so a search that matched results would either refuse to replace or destroy the formula that produced them. Excel's default "Look in: Formulas" behaves the same way.
- **Case-insensitive matching is ASCII-only** — full Unicode case folding changes byte lengths (`İ` lowercases to two chars), so an offset found in a folded haystack does not point at the same place in the original, and splicing a replacement at it corrupts the surrounding text. `to_ascii_lowercase` is length-preserving. Non-ASCII users get exact matching with "Match case" rather than silently mangled cells.
- **A replacement that would not parse as a formula leaves that cell alone** rather than failing the whole operation part-way through.

**xlsx formatting**

- **Import parses `xl/styles.xml` into our model *and* keeps every cell's original `s` index; export writes that original index back for any cell whose format did not change** — so opening and saving a workbook without touching its formatting leaves the style sheet byte-identical, including every attribute we do not model (typefaces, theme colours, vertical alignment, diagonal borders). A test asserts exactly that, because "we preserve formatting" is the kind of claim that quietly stops being true.
- **A changed cell gets a *newly appended* `<xf>`, never a rewritten one** — appending keeps every existing index pointing at the same record, so parts of the package we never parsed stay correct. Rewriting in place would silently repaint every other cell that shared the style.
- **A synthesized font copies the original font's `sz`, `name`, `family`, `scheme` and `u` children verbatim** — bolding an 8pt Garamond cell must produce bold 8pt Garamond, not bold 11pt Calibri.
- **Theme and indexed colours read as "no colour" rather than being resolved** — they resolve through `xl/theme/` and a legacy palette we do not parse, and guessing black would be wrong in a dark theme. Because an unchanged cell keeps its original index, they still round-trip perfectly; they simply do not appear in the model.
- **A style sheet we cannot parse is a warning, not a fatal error** — the cells still import, they just arrive unformatted, and the preserved indices keep the round trip lossless.
- **Formatting a workbook whose package has no `xl/styles.xml` fails loudly** — adding a new part means touching `[Content_Types].xml` and the workbook relationships, the same gap that blocks adding a sheet to an imported workbook.
- **Import writes `Sheet::formats` directly instead of replaying `FormatApply` actions** — the file's existing formatting is initial state, not something the user did in this session. The importer already builds its `Engine` directly for the same reason.
- **`Engine::clear_history()` is called at the end of every import** — import replays a file cell by cell through `apply`, which is what keeps the importer honest, but it also meant a freshly opened workbook arrived with one undo entry per imported cell and the user's first Ctrl+Z un-typed a cell they never typed.
- **Splice edits are ordered by `(start, end)`, not `start`** — when a zero-length insertion shares an offset with a replacement, sorting on `start` alone leaves their order to sort stability, and the replacement overwrites the text the insertion just placed. That bug produced a corrupt style sheet on the one path that inserts a missing `<numFmts>`.

**Grid and UI**

- **The viewport sends per-cell format *indices* plus a small palette, not per-cell objects** — a formatted block is overwhelmingly repetitive; a bold header row is one palette entry and N small integers rather than N copies of the same object crossing the wasm boundary every frame.
- **Number formatting is applied in Rust, inside `viewport`** — `numfmt` already implements Excel's format codes for `TEXT`, and a second implementation in TypeScript would drift. The grid draws text; deciding what the text says stays with the engine.
- **`SheetInfo` reports both `used_*` (data extent) and `painted_*` (everything drawable)** — Ctrl+Down should stop at the last value, but the scrollable area has to include a bold empty column.
- **Clicking anywhere in a merged block selects the whole block, and dragging a selection expands to contain any merge it touches** — otherwise the cursor can land on a cell the user cannot see, and a partially-selected merge makes every subsequent operation ambiguous. Expansion iterates to a fixed point, because absorbing one merge can bring the selection into contact with another.
- **A merged block is painted by covering it and re-stroking its outline, after the gridlines** — cheaper and simpler than teaching the gridline pass to skip interior segments, and it keeps the single-pass gridline path intact.
- **Drag autoscroll ramps with distance past the edge** — a fixed step makes selecting a long range either unbearably slow or impossible to stop on the right row.
- **`GRIDLINE_CHROMIUM` overrides the Playwright browser** — some sandboxes ship a Chromium whose build number does not match the one Playwright expects and cannot reach the download host; pointing at the binary that is already there beats not running the suite.
- **`window.__gridline__` exposes `stateSnapshot` and nothing else, in dev builds only** — the grid is a canvas, so the end-to-end suite has no DOM to assert formatting against. It is deliberately read-only: a test-only route into `apply` would be exactly the side door the single-mutation-path invariant exists to forbid.
- **`rust_xlsxwriter`'s `wasm` feature is enabled for the wasm32 target only** — the crate stamps each workbook with the current time, and `SystemTime::now()` traps on `wasm32-unknown-unknown`. Every xlsx export from the browser panicked with `RuntimeError: unreachable`; the bug had been latent since M2 because nothing in the UI called export until M5. No native test can catch a regression, so the guard is the end-to-end test that saves a workbook in a real browser and opens it again.

## M6 — Miner

- **Mining runs on abstract tokens, never on raw events** — `=SUM(B2:D2)` in E2 and `=SUM(B3:D3)` in E3 are one habit repeated, and a tokenizer that kept the addresses would never notice. References are normalized to R1C1 offsets from the writing cell, which is exactly what collapses a filled-down column into one repeated token.
- **Literal values never enter a token, even under `full` capture** — the habit is "typed a number here"; the number is what we promised not to mine. A hashed literal and a verbatim one produce the same token, so mining behaves identically in both capture modes.
- **The unparseable-formula fallback scrubs strings and sheet qualifiers** rather than passing the raw text through. Whole-column references (`A:B`) do not parse in v1, so that fallback is the path a real workbook takes — and it would otherwise have been the leak the careful path exists to prevent.
- **Two miners, not one.** Tandem repeats catch a loop the user ran by hand in one sitting and need no cross-session support; PrefixSpan catches a habit spread across sessions and needs three. Neither finds the other's answers.
- **A tandem repeat may never span a session boundary** — three sittings that each start the same way concatenate into what looks like a loop, and calling it one both overstates the evidence and puts "repeated 3 times in a row" in front of a user for whom it never happened. Caught by a planted-pattern test, not by the unit tests.
- **Only primitive periods are reported** — `a b a b a b a b` has a period of 4 as well as 2, and proposing the longer one would offer a routine that does the work twice.
- **PrefixSpan counts support by session, not by occurrence** — one busy afternoon is a loop, and letting a single session mint support would make every busy afternoon look like a habit.
- **Only maximal patterns are proposed** — offering both `a b` and `a b c` is offering half a routine alongside the whole one.
- **Review cost is charged once per routine, not once per repetition** — the first version charged it per occurrence, which priced in re-reading the same preview twelve times and made a genuine twelve-row habit score below the threshold and vanish from the panel.
- **Scoring is backward-looking**: "you have already spent this long", which a user can check against their own memory, rather than a projection of future savings, which they cannot.
- **A routine is synthesized from a real occurrence, not from the tokens** — tokens are deliberately lossy, so building from them would mean inventing the details back. The most recent occurrence is the template, on the grounds that the user's latest way of doing something is most likely to still be right.
- **A routine keeps the coordinates it was recorded at, plus its anchor, and is shifted once when it runs** — normalizing the actions to the origin first looks tidier and is quietly wrong: `=SUM(B5:D5)` written in E5 points three columns left, so moving it to A1 walks off the grid and the reference collapses to `#REF!` before it can be moved back.
- **What cannot be rebuilt is stated, not guessed** — a redacted literal becomes a `Requirement` the routine reports and does not perform, and a paste is skipped entirely because the log records its shape but not the clipboard. A routine that pasted the wrong block would be far worse than one that does not paste.
- **A routine runs through `Engine::apply` like everything else** — no second execution path, so it can do nothing the user could not have done by hand, and every action it takes is captured like any other.
- **The dry run clones the engine rather than applying and undoing** — undo is itself engine behaviour, and a preview that leaned on undo being correct could not show the user a bug in undo. The diff includes downstream recalculation, which is most of the point.

**Routines: where the pieces live**

- **`Routine`, its shift logic and the dry-run sandbox live in the engine, not the miner** — the miner discovers routines, the server stores them and the client runs them, so three things need the definition and it must be one definition. The same reasoning that put telemetry in the engine. What stays in the miner is discovery: `synthesize`, `reconstruct` and the summary, which are all about reading a mined pattern back into actions.
- **The miner writes the `routines` table directly** rather than posting to an endpoint. The server's own doc comment already said this is the arrangement ("the miner writes rows here; the server only serves them back and records feedback"), and an HTTP path would need an admin credential and a second copy of the schema. The miner keeps a copy of the table definition for its in-memory tests, and a test compares that copy against the migration so the two cannot drift silently.
- **Re-mining updates a proposal; it never duplicates one** — the routine id is derived from the pattern's token shapes, so a nightly run over a growing log refreshes support and estimate in place.
- **A verdict the user has given is never overwritten.** A dismissed routine stays dismissed no matter how strong the evidence gets; asking again every morning is how a good feature becomes an irritating one. The *body* is still refreshed, so an accepted routine keeps working as the log grows.
- **Proposals the log no longer supports are pruned; answered ones are not.** A panel that only grows stops being read, but a dismissed row is the user's answer rather than our suggestion, and deleting it would resurrect the suggestion on the next run.
- **Mining is per (actor, workbook)** — a habit belongs to the person who has it, and pooling two people's logs would manufacture support neither of them earned.
- **The wasm bridge hands back a routine's actions rather than running them.** `routineActions` returns the shifted `Action`s and the client pushes them through the same `applyBatch` every other gesture uses. Running them inside the engine would be a second execution path — exactly the side door the single-mutation rule exists to forbid — and the capture pipeline would have to be taught what a routine is instead of just seeing the actions.
- **A routine is run as one batch**, so it lands in one undo step: a suggestion the user has to press Ctrl+Z five times to reject is not a suggestion.
- **Every proposal previews before Run is available**, against the current selection, computed by the same engine the run will use. A routine that would change nothing here says so and disables Run; one the engine would refuse shows the refusal before the click, not after.
- **A partial routine names the cells it cannot fill** and runs the rest. "The log only has a hash of that number" is a fact about what we chose not to record, and hiding it would make the routine look broken instead of honest.
- **A server the panel cannot reach is a line of text in the panel, not an error toast** — no suggestions is not a broken spreadsheet.
- **The dry run diffs formatting as well as values.** The first version compared cell values only, so a routine that bolds a header row previewed as "nothing would change" and the panel disabled Run on a routine that worked perfectly well. Format changes are reported separately and described in words, because "B2 becomes bold" and "B2 becomes 47" are different enough that one column would read as noise.
- **`Engine::apply_batch` coalesces the undo entries its actions push into one.** Applying in a loop pushes one per action, which made the panel's own promise — "runs in one undo step" — false, and meant rejecting a five-step routine took five Ctrl+Z. Caught by the browser suite; nothing had used `applyBatch` until routines did.

## M7 — Demonstration dataset

- **A record is `{pre_state_digest, context, action, post_state_digest}` and never the state itself.** A digest identifies a state without disclosing it, which is what lets the dataset say "from here the user did this, reaching there" while carrying none of their data. The digest is SHA-256 of the same `state_snapshot` the replay suite compares, so "same digest" means exactly what a passing replay test means.
- **Redacted literals replay as placeholders derived from their hash, and the record says so.** Under `structural` capture the real values were never recorded, so there is nothing to replay; deriving the stand-in from the hash preserves the one property the dataset actually needs — equal values stay equal, different ones stay different — so a lookup finds its match and a conditional aggregation counts the right rows. `values_synthetic` is on every record, because a consumer that mistook these for the user's numbers would be drawing conclusions from noise.
- **A placeholder keeps its original's type.** A number stays a number and text stays text (apostrophe-forced, so a placeholder that looks like a number or a formula still lands as text), because `=A1+A2` over two text placeholders is `#VALUE!` and the record would be worthless.
- **Each session replays from an empty workbook.** A session is the unit a demonstration is read from; carrying state across one would make every record after the first depend on work the reader cannot see. It also means two sessions that did the same thing produce the same digests, which is how the dataset is checked.
- **An action the engine refuses is counted, not recorded.** Its pre and post digests would be identical, and a record of that teaches a reader the action is a no-op rather than that it was refused.
- **Consent is a `WHERE` clause, not a filter over the results** — the same predicate the server's own export uses. A filter can be forgotten; a join cannot. Latest consent wins, `off` and revoked are excluded, and an actor with no consent row at all contributes nothing.
- **`--consented-only` is mandatory for a database export rather than the default.** An operator who has to type it cannot later say they did not know the export was filtered, and a flag that must be typed cannot be quietly dropped from a copied script. It is *refused* with `--in`, because a JSONL log carries no consent records and accepting the flag there would let a script claim a check that never ran.
- **The miner's test database is the server's migration, run verbatim.** The earlier arrangement — a hand-copied `routines` table plus a drift test — could not cover the consent query, which is only worth anything against the real `consents` table. `include_str!` on the migration was already crossing that boundary anyway.
- **One JSONL file per session, named `NNNN-<session-id>.jsonl`, plus a `manifest.json` naming exactly the files that belong to the dataset.** Session ids arrive from a client, so the filename is sanitized to alphanumerics and truncated: an id of `../../etc/passwd` must land inside the output directory as a mangled name. The numeric prefix makes collisions between two ids that sanitize alike impossible. Stray `.jsonl` files from an earlier run are reported rather than deleted — they would read as part of the dataset to anyone globbing the directory, but removing a file the operator put there is not ours to do.

**Sheets in an imported package**

- **Worksheet parts are tracked by `SheetId`, never by name.** Matching on the name makes a rename indistinguishable from deleting one sheet and adding another, and the renamed sheet would silently lose everything its part held that we do not model: its columns, its conditional formatting, its drawings. Sheet ids are monotonic and restored by undo, so the mapping survives an undone delete.
- **The package is spliced, never regenerated.** `xl/workbook.xml`, `xl/_rels/workbook.xml.rels` and `[Content_Types].xml` are edited by byte range: a rename rewrites one attribute, an addition inserts one element before each closing tag, a deletion removes exactly the elements that named the departed part. When the sheet list is unchanged, none of the three is written at all — which is the only way to keep the promise that opening and saving a file changes nothing it did not have to.
- **A new sheet's part is generated empty and then patched by the same writer as every other sheet**, so there is one code path for writing a worksheet rather than two that can disagree.
- **New relationship ids clear every existing one, not just the worksheet ones.** `rId2` is often a VBA project or a theme; allocating the next free *worksheet* id would collide with it.
- **A new part's filename is the first free `sheetN.xml`, which need not match its `sheetId`.** The two are unrelated in the format, and pretending otherwise breaks on any file whose author deleted a sheet before us.
- **Deleting a sheet drops `xl/calcChain.xml`; renaming one does not.** The chain is keyed by sheet index, so adding or removing a sheet renumbers it and Excel offers to repair the file. It is a cache: dropping it costs a recalculation on open. A rename renumbers nothing, so throwing the cache away would be a cost paid for no reason.
- **A package with no `xl/styles.xml` is given the default one at import, not at export.** Formatting then always has somewhere to go, and every later stage has one case to handle instead of two. The default records matter: index 0 of each collection must be the real default, because a cell with no `s` attribute means `s="0"` — appending into empty collections would make the first format anyone applies the default for the whole workbook.
- **Verified against an independent reader.** The round-trip tests use our own importer, which would happily read back a file only we can parse; the add/rename/delete output was additionally opened with `openpyxl` to confirm a third-party reader agrees about the sheet list and the formulas.

**The demo**

- **The demo is a script, not a rehearsal.** `scripts/demo.sh` seeds a database, mines it, exports the dataset and checks the consent refusal, all from an empty directory. Every piece goes through the real path: the events are built by `engine::telemetry::describe`, the same function the browser calls through wasm; the rows land in the schema the migrations declare; the consent test is the export's own query. A seeder that fabricated payloads would demonstrate a system that does not exist.
- **The seed includes an actor who declined.** The export refusing to carry them is the claim worth making, and it can only be *shown* if there is something it could have taken. `scripts/demo.sh` greps the output for their sessions and fails if it finds any.
- **The seeder writes the worked workbook, not just the log.** A log claiming twelve rows were added and a file containing five is a demo that contradicts itself. The workbook is exported through the preserved package, so what the presenter opens is the fixture with the scripted work in it.
- **The rate card is referenced absolutely (`Rates!$A$1:$B$3`).** It was relative, which is a bug waiting in a real ledger — fill the row down and the lookup walks off the table — and it also made every row of the ledger a *different shape* to the miner, so the habit was invisible. The fix is in the sheet, not in the normalizer: a relative reference genuinely does mean something different in every row.
- **The summary block moved below the member table and reads a range with room in it.** A total that stops at the fifth row goes quietly wrong on the sixth, and a ledger the demo appends to needs somewhere to append.

**What running the miner on real data changed**

- **A loop explains the steps it covers; nothing else may count them as evidence.** Twelve identical rows typed over three sittings produced **155 proposals**: every subsequence straddling a row boundary reached support, and the ones that hit `max_length` looked maximal only because the search stopped there. Masking the steps a tandem repeat covers takes it to one. The masked steps are skipped, not deleted — they still occupy their positions, so the work either side of a loop does not become spuriously adjacent.
- **Identical loops from different sittings merge into one proposal.** The detector works per session, so a habit run every morning arrived as three identical patterns; proposing each separately offered the same routine three times and understated what it saved.
- **A merged loop does not say "in a row".** Twelve repetitions across three mornings is not twelve consecutive ones, and the summary now distinguishes them. The same reasoning that stopped tandem repeats spanning sessions in the first place.

**What walking the demo in a browser changed**

- **`VITE_DEV_TOKEN` now actually does something.** `scripts/dev.sh` had been printing "the web app reads it from VITE_DEV_TOKEN, so no manual step is needed" since M4, and nothing read it. There is no sign-in screen, so every API call in a `make dev` session came back 401 unless you opened the console and wrote to `localStorage` by hand. The app adopts it at start-up, only in a dev build, and only when nothing is already stored — a token typed in by hand still wins.
- **`VITE_DEV_WORKBOOK_ID` exists for the demo.** The workbook id is minted by the client and kept in `localStorage`, so routines mined for a seeded workbook could never appear in a panel that had invented its own id. Same guards as the token.
- **A requirement that is already filled in is not reported as missing.** The preview said "you will still need to type them" about four cells the user could see on screen, filled in. `DryRun` now reports `unmet` — the subset of `requires` whose target is actually empty — alongside `requires`, and the panel says the values are already in place when they are. Found by looking at a screenshot of the panel, not by a test.

**The demo's own conventions**

- **The ledger labels every column it uses and formats the rows it will grow into.** Six unlabelled columns under a header band is what an unfinished sheet looks like, and a currency band that stops at the last filled row makes the next row someone types look like a different sheet.

**Saying plainly what "formulas are verbatim" costs**

- **A formula's text literals and sheet names are recorded in clear, and the documents now say so where a user reads them.** `structural` hashes every literal value and every sheet name — except the ones written *inside a formula*, because the formula is kept as typed. Reading `PRIVACY.md` and `EVENTS.md` together, a careful user would have concluded sheet names are never disclosed; a dataset record showing `=VLOOKUP(B7,Rates!$A$1:$B$3,2,FALSE)` beside a hashed `context.sheet` says otherwise. Found while checking the new `DATASET.md` against a real exported record, which is the point of writing documentation against output rather than against intent.
- **The disclosure was documented, not redacted.** Blanking string literals inside formulas would break the dataset — a replay of `=IF(F7<=0,"","")` computes something the user never saw — and the mining pipeline already reduces formulas to shapes with the text blanked and the sheet qualifier anonymised before it looks for a pattern. What was wrong was the description, not the behaviour. The consent notice, the transparency page, `PRIVACY.md`, `EVENTS.md` and `DATASET.md` now all say the same thing, and the honest advice for a sensitive sheet name is `off`.

## P0 — The parity harness

- **The harness came first, and it found things immediately.** Five differences on the first serious pass, none of which any existing test had: Excel's final-result rounding to 15 significant digits (so `=0.1+0.2=0.3` is TRUE in Excel and was FALSE here), General switching to scientific notation for large magnitudes, the negative section of a number-format code, the 1900 leap-year bug, and arithmetic overflow returning IEEE infinity. That is the argument for building the measurement before the features.
- **`inf` was fixed rather than recorded.** The other four are fidelity gaps; this one was a non-value escaping into the product. Every operator except `^` would hand back an infinity, and it would have travelled from the grid into the state snapshot, the event log and the exported dataset. Recording it and moving on would have been process worship.
- **Every case cites its provenance, and the report says Excel was never run.** `known` is documented or universally reproduced behaviour, `spec` is a citation, `open` is unsettled. A corpus of confident assertions with no stated source is not an oracle — it is the same opinion the engine already has, written down twice, and a score computed from it would invite the reader to believe a comparison that never happened.
- **`open` cases are excluded from the score, not guessed at.** Both semantics pinned back in M2 — whether `COUNTIF` propagates an error found in its range, and what approximate lookup does on unsorted data — are recorded with every candidate answer and with what Gridline currently does. Someone with Excel in front of them can settle each in one line.
- **A `known_difference` counts against the score but does not fail the build**, and a recorded difference that *starts* matching does fail it. CI's job is to catch a regression, not to re-report a number somebody already wrote down; and a corpus still claiming a divergence that has been fixed is a lie in the other direction.
- **LibreOffice was evaluated as a live oracle and rejected.** It is installed here but cannot load any file in this sandbox — and more to the point, it is a different implementation with its own divergences, so agreement with it is evidence about LibreOffice. The corpus format is unchanged by adding a real oracle later: it would supply `expect` values with a stronger source.
- **The target function list names functions we have not written.** A target naming only what exists reports 100% coverage forever. Tier 1 is the v1 scope and tier 2 is the next set worth having, which is what makes 48.5% a number rather than a formality.
- **Coverage counts "pinned by a case" separately from "implemented".** A function that exists but no case exercises is tested against nothing but our own opinion of it, and the report says which those are.
- **`PARITY.md` is generated, committed, and checked in CI** — the same arrangement as the golden fixtures, for the same reason: a score that only exists in a CI log is a score nobody reads, and one that can change without a diff is a score nobody can trust.

## P1 — Closing the measured differences

- **Number-format sections are implemented.** A code has up to four — positive; negative; zero; text — and the negative one formats the *absolute* value, because in `0;(0)` the parentheses carry the sign and a minus as well would say it twice. A section with no digit placeholder is a literal, which is how `0;(0);"zero"` shows a word where a zero would be, and an empty section shows nothing, which is how `0;;` hides them. Bracketed colours and conditions are still out of scope: a half-understood `[Red]-0` would be worse than falling back to General.
- **The old test asserted the absence of the feature.** `general_and_unsupported_fall_back_to_display` pinned `0.00;(0.00)` to `5`, which was the limitation written down as though it were behaviour. Exactly the pattern the handoff warns about, and worth noticing that it was found by implementing the feature rather than by reading the test.
- **Serial 60 now has components, and still has no date.** The M2 decision — `#NUM!` rather than a fake 1900-02-29 — said to revisit it if the oracle corpus demanded, and it did. `YEAR`/`MONTH`/`DAY` answer 1900, 2, 29, because they are asking what Excel calls this serial and a workbook containing it would otherwise read as an error; `serial_to_date` still returns `None`, because month arithmetic needs a date to count from and handing it a fiction would spread it into EOMONTH and EDATE. `DATE(1900,2,29)` returns 60. What is *not* covered is a rollover that lands on the phantom day (`DATE(1900,1,60)`), which needs Excel's calendar rather than the real one; it is recorded as a difference rather than left silent.
- **The scientific-notation case was withdrawn, not fixed.** Excel's General switches to scientific when the number does not fit *the column*, so what it shows depends on the width — and `Value::display()` has no width. Asserting `1E+20` would have manufactured a difference out of a question the corpus cannot ask. Reclassified as open, with the width-independent part of the rule named as what still needs settling. A case that cannot be well-founded should be withdrawn rather than kept because it is already written.
- **The two float-rounding differences stay recorded.** Excel rounds a final result to 15 significant digits before comparing, which is why `=0.1+0.2=0.3` is TRUE there. The rule has to be applied at the same point Excel applies it — the mechanism appears to be the subtraction inside a comparison, not a per-cell rounding — and guessing that point would trade one wrong answer for a subtler one.
- **The harness failed silently on its own success case.** A `known_difference` that starts matching exits 1, and the CLI printed nothing about why: it only reported `Differs`. Found by using it. A tool that tells you it failed without telling you what failed is worse than one that does not check.

## P2 — Tier-2 functions

- **The cases were written before the code, and they caught the sign rules.** CEILING and FLOOR round towards or away from zero depending on the signs of *both* arguments, which Microsoft's own page spends a paragraph on; MROUND refuses mixed signs where CEILING accepts them; SIGN(0) is 0 where IEEE `signum` gives 1. Writing the expectation first is what made those decisions rather than accidents — and mutation-testing two of them afterwards confirmed the cases would have caught a wrong implementation.
- **Three predicates for errors, because "missing" and "broken" are different.** ISNA is #N/A alone, ISERR is every error except it, ISERROR is all of them. The same split gives IFNA its reason to exist beside IFERROR: a failed lookup is expected and a #VALUE! is a bug, and wrapping a VLOOKUP in IFERROR hides both.
- **RANK is a competition ranking, not a dense one.** Ties share the best rank and the next is skipped, so two values tied at 2 are followed by 4. The corpus pins both halves, because an implementation that answers 3 passes every test that only checks the tie itself.
- **The new functions are covered by the parity corpus rather than by duplicate unit tests.** `cargo test --workspace` runs the corpus, so they are tested where CI looks; a second copy of the same expectations in the engine crate could only drift from the first.
- **Dynamic arrays are out of scope until spilling exists.** UNIQUE, SORT, FILTER, SEQUENCE and TEXTSPLIT return ranges rather than values, which is a change to the model and not a function to write. They stay on the tier-2 list so the coverage number keeps counting them as missing.

- **`EvalCtx` carries the cell being evaluated, added for `ROW()` and `COLUMN()`.** Nothing else in the evaluator had needed to know where it was, which is why it took until the reference functions to appear; there is one construction site, so the change cost a line.
- **A lone cell reference reaches a function as a scalar, and `ROWS(B5)` has to be 1 anyway.** The evaluator degrades a 1x1 range before the function sees it, so `ROWS` and `ROW` read the address out of the *expression* when the operand came back scalar. Worth the special case: `ROWS(A1)` erroring would be wrong, and `ROWS(3)` not erroring would be worse.
- **SUMPRODUCT works over ranges and not over computed arrays.** `SUMPRODUCT(A1:A3,B1:B3)` is right; `SUMPRODUCT((A1:A3>2)*1)` — the pre-COUNTIFS conditional-counting idiom — answers `#VALUE!`, because an operator applied to a range degrades it to a scalar. Element-wise operators are the same model change dynamic arrays need, so it is a recorded difference rather than a special case inside one function.
- **Text is zero inside SUMPRODUCT, and a shape mismatch is refused.** The first is what lets a comparison select rows; the second is because two columns of different length nearly always means one of them points at the wrong rows.
- **The coverage unit test names a function that will never exist.** It used `SUMPRODUCT` as its stand-in for "not implemented", and broke the moment SUMPRODUCT was implemented — failing for a reason that had nothing to do with what it was testing.

- **The financial functions are one equation rearranged, and the module says so.** PMT, FV, PV and NPER are algebraic solutions of `pv(1+r)^n + pmt(1+r·type)((1+r)^n−1)/r + fv = 0`; RATE and IRR have no closed form and are bisected. Writing them as separate derivations would have meant six chances to get the `type` term wrong instead of one.
- **RATE and IRR bisect rather than following Newton's method.** Slower, and it cannot wander off to a nonsensical root on a badly conditioned cash flow. When the bracket holds no sign change the answer is `#NUM!` — the same thing Excel says when its own iteration gives up — rather than whichever end happened to be nearer.
- **IRR refuses a cash flow that never changes sign.** There is no rate at which the present value of an all-positive series is zero, and returning a number anyway would be returning the search bracket.
- **Excel's sign convention is reproduced, and it is most of what makes these agree with a real schedule.** A loan is a positive `pv` because the bank gave you the money, and `PMT` comes back negative because you pay it back. Getting it backwards produces answers that look plausible.
- **The expectations were computed from the documented equation, independently of the implementation, and the iterative ones were checked by substitution** — residuals of 1.2e-9 and -5.4e-10. `known` here means the equation is documented, which the corpus header says rather than implying a copy of Excel confirmed the digits.

- **`COUNTUNIQUE` came off the target list.** It is a Google Sheets function; Excel spells that `COUNTA(UNIQUE(...))`. A target list naming functions Excel does not have makes the coverage score unreachable for a reason that has nothing to do with the engine, which is a worse fault in a measurement than being incomplete.
- **`SUBTOTAL` skips filter-hidden rows, which is the entire reason it exists** — a plain `SUM` under a filtered table is usually the wrong formula. Codes 101-111 additionally skip *manually* hidden rows; Gridline has no manual hiding, so they behave identically today, and the corpus case says where the two will diverge when it arrives.
- **`XMATCH`'s wildcard mode shares COUNTIF's matcher.** Two implementations of `*` and `?` would eventually disagree about what a pattern means, and the disagreement would surface as one function finding a row the other does not.
- **`ISREF` is decided from the expression, not the value.** By the time a value reaches a function there is nothing left to tell a cell from the number in it.
- **`OFFSET`, `INDIRECT` and `TRANSPOSE` are deliberately absent.** They return *references*, and a function in this engine returns a `Value` — so `SUM(OFFSET(A1,0,0,3,1))` could not work. A scalar-only version would handle `OFFSET(A1,1,1)` and fail on the common use, which is worse than not having it: the report would count it as implemented.

- **A second weekday mapping was wrong within an hour of being written.** `NETWORKDAYS` counted weekends with `serial mod 7`, reasoning from "serial 1 is a Monday" — and it was a day out, because Excel's serial line contains a phantom 1900-02-29 and a modulus over it does not line up with the weekday the rest of the engine reports. `WORKDAY(Friday, 1)` answered Sunday. Weekends are now asked of the calendar date, where `WEEKDAY` asks. The same lesson as XMATCH's wildcard matcher, learned again in the opposite order: there it was avoided by sharing, here it was caught by the harness.
- **`YEARFRAC`'s actual/actual basis is an open question, not a claim.** The other four day counts are arithmetic anybody can check; basis 1 is the one whose exact definition is genuinely disputed, and the corpus records all three readings with what Gridline currently does. A confident-looking wrong number there is a bond priced wrong.

## P3 — Reference-returning functions

- **`eval_operand` asks `call_operand` first and falls back to the value path.** `OFFSET` used as a range argument and `OFFSET` used as a scalar therefore go through the same code: the range is produced once, and a scalar position reads its top-left cell exactly as a written reference does. Two entry points would have been two behaviours.
- **`scalar_of` was extracted rather than duplicated.** A reference-returning function already holds an operand; going back through the expression to get a scalar would evaluate it twice, and for a volatile function that is not merely wasteful.
- **The stale-read hazard was real, and the first test I wrote for it passed by accident.** `OFFSET`'s *base* is written in the formula, so the dependency graph does see it — my first attempt made the volatile cell depend on its base and proved nothing. The genuine case needs the offset *window* to cover a formula cell that the graph cannot see and that sorts later: `A1 = SUM(OFFSET(A2,0,0,3,1))` where `A3` is a formula. That one read 10 where it should have read 50.
- **The fix is bounded iteration, and only for computed references.** `OFFSET` and `INDIRECT` read cells the graph never saw; the clock and random functions recalculate every pass but read *nothing*, so their answers cannot be stale and an extra pass would buy nothing but a different random number. `Expr::has_dynamic_reference` draws that line, and a sheet with no `OFFSET` pays nothing.
- **The dynamic-reference set is scanned, not tracked.** The volatile set is small by nature, and a second set to keep in step with it is a second thing to forget updating — which is how the first weekday mapping went wrong.
- **`INDIRECT` does not accept the A1/R1C1 style flag.** R1C1 is not a syntax this engine reads anywhere, and accepting the argument while ignoring it would silently return the wrong cells.

## P3b — Column widths and row heights

- **Sizes moved out of React and into the engine.** A width was `useState` inside `Grid`, so it survived until the next reload and was invisible to the file, the undo stack and the capture log. It is a thing the user *did*; the single mutation path is where those live. The grid now keeps only the size being dragged, as a preview, and hands the final number to `Action::Resize`.
- **`Resize` names a run, and `size: None` is "back to the default".** A drag resizes one; a multi-column selection resizes several; autofit resizes each to its own measured width, which arrives as several actions in a batch. Clearing to the default *removes* the entry rather than writing the default down, so a reset leaves no `<col>` behind in the file — and a second action for "reset" would have been a second thing for routines to learn.
- **A width has to be a width.** Zero and negative are refused rather than clamped, because a zero-width column in Excel is a *hidden* column — a different feature — and accepting one here would have made a hiding gesture out of a resize by accident.
- **The model stores pixels; the file stores neither.** A column `width` is a count of characters of the font's maximum digit width plus padding, and a row `ht` is in points. `io/sizes.rs` uses the two documented formulas rather than an approximation, because they are exact inverses over the pixel range a grid can produce — and a conversion that drifts by a pixel per save is invisible on the first save and unrecognisable on the twentieth. `widths_survive_a_round_trip` holds every value from 6 to 2000 pixels to that.
- **`rust_xlsxwriter` means something else by "pixels".** Its `set_column_width_pixels` takes the width *inside* the column and adds Excel's five-pixel padding itself. Handing it a rendered width widened every column by five pixels on each save, which is exactly the drift the paragraph above is about, and it was caught by the sweep rather than by the single-width test that preceded it.
- **`<cols>` and `ht` are only rewritten when a size actually moved.** They are compared against what import read, the same way merges are. `width="24.5"` is not a number our arithmetic produces — it comes back as 24.43, which is the same pixel — and rewriting it on every save would renumber every column of every file anyone opened without changing what they look like.
- **A `<col>` covering the whole sheet is expanded on import and coalesced on export.** `min="1" max="16384"` is common, and a cap would silently drop the width of every column past it; sixteen thousand map entries cost a couple of hundred kilobytes, and export writes them back as the one element they came from.
- **Sizes shift with insert and delete.** A width belongs to its column and travels with it. Leaving it behind on whichever column slid into the slot is the sort of wrongness nobody can point at afterwards.
- **`state_snapshot` gained the sizes, as runs.** The parity harness's "state identical" claim is only worth what the snapshot covers, and drift in a width is precisely what it should catch. Runs rather than one entry per index, because a snapshot is meant to be read.
- **`npx tsc --noEmit` checks nothing here, and I used it anyway.** The root `tsconfig.json` is `"files": []` plus project references, so the bare invocation type-checks an empty program and exits 0 — it accepted a deliberately undefined type when I tested it. CI has been right all along (`npm run build` is `tsc -b && vite build`, with a comment saying exactly this); the fault was mine, verifying with a command that could not fail. `tsc -b` then caught a genuine error in the first pass of this change.

## P3c — The system clipboard

- **Clipboard *events*, not the clipboard API.** `navigator.clipboard.readText()` needs a permission prompt; the browser's own `copy`/`cut`/`paste` events hand over a `DataTransfer` with no prompt at all, because the user pressing Ctrl+V *is* the permission. The cost is that Ctrl+C/X/V had to come out of the keydown handler — calling `preventDefault` there suppresses the very events this needs.
- **Copy writes both `text/plain` and `text/html`.** TSV is what a text editor and a spreadsheet both understand; the HTML table is what makes a cell containing a newline unambiguous. On the way back in the table wins for that reason, and TSV is the fallback.
- **The TSV reader is a scanner, not a `split`.** A field may be quoted and contain tabs and newlines, a trailing line break ends the last row rather than starting an empty one, and `5"` is a measurement rather than an unterminated quote. Each of those is a test, and each of them is a paste that would otherwise land wrong.
- **An internal paste and an external paste are different operations, and the clipboard text decides which.** Copy remembers exactly what it put on the system clipboard; if that is still what is there, the paste goes through `range_paste`, which carries formulas and moves their references. If it is not, someone else's text is on the clipboard and it lands as cell edits. Comparing the text rather than trusting a flag is what makes "I copied in Gridline, then copied something in Excel, then pasted" do the right thing.
- **An external paste is one batch, so it is one Ctrl+Z.** Four cells arriving as four undo steps would be four rejections for one gesture.
- **`applyBatch` had been capturing only the first action of a batch**, under a comment claiming the opposite. Found by asking the pasting test what reached the ingest endpoint: four cell edits went in, one event came out. That makes the log replay to a different workbook than the user is looking at, and a routine mined from it would be the first fifth of a habit. Routines had been shipping through the same path since M6.

## P4 — Dynamic arrays

- **An operator over anything wider than a cell is element-wise.** `Operand` gained an `Array` variant and `eval_binary` was split into a free `apply_binary` so the element-wise path can combine values it already holds rather than re-evaluating the expression once per cell. This is what closed the recorded `SUMPRODUCT((A1:A3>2)*1)` difference — it was never about SUMPRODUCT.
- **Broadcasting follows Excel, including the ragged case.** A single row repeats down, a single column repeats across, and a 3-row against a 2-row gives three rows with `#N/A` in the third rather than two rows or an error. Padding with `#N/A` is what makes the mismatch visible instead of plausible.
- **A block in scalar position is still `#VALUE!`.** Implicit intersection is not implemented, and a block is treated exactly as a range is — one cell degrades, anything larger says so. Guessing which row was meant would be worse than refusing.
- **Placement is one deterministic sweep, not a race between formulas.** `eval_and_store` records the block; `place_spills` lays every one of them out afterwards, in address order, across the whole sheet. Doing it inline as each formula evaluated would have made the layout depend on the dependency graph, and two paths to the same workbook could then disagree — which is the replay invariant, broken.
- **A real cell always beats a block, whichever came first.** Anything in the way blocks the *whole* block: a half-spilled array is worse than an error, because the user cannot tell which half is the formula's. The anchor says `#SPILL!`.
- **Blocked-ness is sticky across passes.** The first attempt flipped the anchor between its first element and `#SPILL!` on alternate passes, and whichever pass ran last won — not a rule anyone could rely on. `Engine::spill_blocked` carries the last placement's verdict into the next evaluation, and `place_spills` is the only thing that writes an anchor's value.
- **Spilled cells are read through `Sheet::value` and are in the used range.** They have no `Cell`, so anything reading `cells` directly sees blanks — which is how the browser grid painted a working block as empty until the viewport was fixed. `used_range`, `painted_range`, CSV export and Ctrl+Down all go through the right door now; the viewport did not.
- **A formula reading a spilled cell recalculates when it changes.** The dependency graph is built from written references and knows nothing about a cell nobody wrote. `place_spills` returns what moved and `recalc` seeds another pass with it, bounded the same way the dynamic-reference loop is.
- **The state snapshot carries the spill.** Two workbooks that differ only in where their blocks landed are different workbooks, and a snapshot that could not tell them apart would make the determinism test pass for the wrong reason.
- **`Expr::Name` replaced the parse-time `#NAME?`.** An unknown identifier used to become an error node in the parser; `LET` binds names, so which ones are known is not something the parser can decide. Unbound names still answer `#NAME?`, and the old test was rewritten to say that rather than deleted. The miner renders a bound name as `NAME`, because what the user called their intermediate is their content, not the shape of the gesture.
- **`LET` refuses a reference as a name.** `LET(A1,5,A1)` would shadow the cell for the rest of the formula, and a formula whose `A1` sometimes means the cell is unreadable.
- **AGGREGATE's two quartile conventions were written as one and the corpus caught it.** 17 is inclusive and 19 exclusive; they differ in where the ends of the data sit, and the first implementation divided by four in both branches. The pair of cases is the point — either one alone passes an implementation that has only one formula.
- **The exclusive percentile can have no answer, and says so.** With two values it is only defined between 1/3 and 2/3; interpolating past the ends would invent data.

## P4b — Excel's 15 significant digits

- **The rule is applied at the comparison and at subtraction, not by rounding every stored value.** A cell holding `0.30000000000000004` really does hold it, and flattening it on the way in would lose precision later arithmetic still wants. What Excel is saying is narrower: a *difference* below its resolution is not a difference. `=0.1+0.2=0.3` is TRUE and `=SUM(0.1,0.2)-0.3` is 0, which were the two recorded differences, and they were recorded as one because they are one rule seen from two sides.
- **"Agrees to 15 significant digits", not an epsilon.** An absolute threshold would swallow `1e-15` as zero, and a column of small measurements would quietly become a column of zeroes. Two boundary cases pin where the line is rather than that there is one: a difference in the 15th digit is a difference, one in the 16th is not.

## P5 — Defined names

- **The model stores what xlsx stores: the text.** A name refers to `Sheet1!$A$1:$B$4`, kept as a string rather than a parsed range, because that is what round-trips — a name can refer to things this engine does not model, and keeping the string means writing back what was read rather than an approximation of it. Evaluation parses it on use, bounded to eight levels so a name that mentions itself stops instead of overflowing the stack.
- **A name is volatile, and that is a cost recorded rather than hidden.** The dependency graph is built by walking the expression, and the expression says `Total`, not `Sheet1!$A$1:$A$9`. Same problem OFFSET has, same answer — recalculate every pass — and the same fix available later: resolve names while building the graph. Until then a workbook where most formulas use a name recalculates fully on every edit.
- **A LET binding shadows a workbook name.** Innermost scope wins, and a formula that bound `total` should not pick up a workbook name of the same spelling halfway through.
- **A definition is validated when it is written, not every time it is used.** `Sheet1!$A$` parses to an error node rather than failing, so storing it would mean the name silently answered `#REF!` forever; a definition that is nothing but an error is refused at the point the user made the typo.
- **A name may not look like a cell.** `A1` as a name would shadow the cell everywhere with no way to say which was meant; so would `R` and `C`, which are R1C1 shorthand.
- **`<definedNames>` is regenerated only when a name moved, and carries over the ones we do not model** — sheet-scoped names and the `_xlnm.` built-ins like print areas. Same rule as `<cols>`, for the same reason. This also required lifting the early return in `package::plan` that skipped rewriting `xl/workbook.xml` when the sheet list was unchanged: names live there too.
- **The stale `<definedName>` after a sheet delete is no longer a known gap.** Names are rewritten with the same visitor that rewrites formulas, so a name pointing at a deleted sheet becomes `#REF!` and a renamed one follows.
- **The address box became a name box.** Excel's rule: an address navigates, an existing name navigates to where it points, anything else defines a new name over the current selection. It is one input rather than a dialog because that is the gesture people already know — and it turned nine end-to-end assertions from `toHaveText` into `toHaveValue`, which is the sort of change worth noticing rather than papering over.

- **Arrow keys step over a merged block rather than through it.** Leaving one moves from its far edge and arriving in one lands on its anchor, both Excel's rules. Without them, arrowing across a merged header walked invisibly through the covered cells and the selection appeared to stop moving — which was the last item on the merge list the grid had never finished.

## P6 — Frozen panes

- **The grid paints a *list* of rows and columns, not a range.** The frozen band and the scrolling region are not adjacent in the sheet — scrolled down, row 1 sits directly above row 900 — so the paint loop indexes `rowsAt[i]` rather than counting from a first row. Every edge in the per-frame tables is asked for its own position instead of being accumulated from the one before it, because the step from the last frozen row to the first scrolling one is not that row's height.
- **Up to four viewport fetches instead of one.** The quadrants are far apart, and a single rectangle spanning the band and the scrolling region would fetch every row in between. Nothing frozen means one rectangle, exactly as before.
- **`contentY`/`contentX` invert the layout for hit testing.** Without them, clicking a scrolled cell landed on whatever row happened to be that far down the *unscrolled* sheet — the geometry and the pointer have to agree, and the only way to keep them agreeing is for both to go through the same pair of functions.
- **Scroll-into-view had to learn about the band, and finding that out is what the browser test was for.** Selecting a frozen header scrolled the whole sheet back to the top, because a frozen cell looked to `scrollToInclude` like a cell miles above the viewport. A frozen cell is on screen by definition and needs no scrolling at all. The geometry unit tests were all green while this was broken; it took driving the real grid to see it.
- **`<pane>` is patched, not regenerated.** `<sheetView>` also carries zoom, gridline settings and the saved selection, so a freeze replaces just the pane element — or opens up an empty `<sheetView/>` to put one inside. Unfreezing removes it rather than writing a zero split, because a `<pane>` with no split is not what "no frozen panes" looks like in a file Excel wrote.
- **A split is not a freeze.** `<pane>` also describes independently-scrolling panes; only `state="frozen"` is modeled and a split stays in the preserved bytes rather than being read as something it is not.
- **One toolbar button, not two.** Freeze and unfreeze are the same gesture in Excel — everything above and to the left of the cursor is held still — and the button says which one it currently means.

## P7 — Conditional formatting

- **The result is derived, like a spilled block.** Recalculation rebuilds `Sheet::cond_formats` from the rules and nothing else writes to it. That is what keeps "why is this cell red" answerable: the answer is always a rule, never a stray `FormatApply` from three sessions ago. It also means the colour follows the value — including through a formula the user never touched, which is the entire difference between a rule and a fill somebody painted once.
- **A rule's formulas are relative to the top-left of its range.** A rule over `A1:A9` testing `A1>B1` means each row against its own B, and the offset is the same transform copy and paste use — one definition of what a relative reference means, rather than a second one that could drift.
- **The first rule to set an attribute keeps it.** Rules merge *under* each other rather than over, so a later "make it bold" cannot repaint an earlier rule's fill. Excel's priority order, expressed as a merge.
- **A rule's format is differential.** Only the attributes it names apply and the cell's own formatting shows through the rest, which is what `<dxf>` means in xlsx and what makes "colour the fill" leave a number format alone. The viewport layers the two into a one-off palette entry rather than interning it: derived state must not reach the workbook's format table.
- **An error never passes a comparison.** Ordering `#DIV/0!` against a number would produce an answer, and the answer would be nonsense — a broken cell is not "greater than zero".
- **A rule is validated when it is written.** Its formulas are parsed once at `CondAdd` rather than once per cell forever, and a rule that sets no formatting is refused because it would do nothing.
- **Clearing takes the rules that live *inside* the selection.** Clearing one cell of a column-wide rule means "not here", which is not something a rule can say; dropping the whole rule would be a surprise, so it is left alone.
- **Rules a file arrived with are preserved, not read.** Reading them means parsing arbitrary `<dxf>` records as faithfully as `cellXfs`, and a half-read rule paints the wrong thing rather than nothing — worse than not reading it. Gridline's own rules are appended after them with dxf ids that start past whatever the file already used. The consequence is recorded honestly: an imported rule still does not display.
- **Both export paths write rules.** The preserved path splices `<conditionalFormatting>` and appends `<dxf>` records; the generated path restates the rule in `rust_xlsxwriter`'s own vocabulary. The mapping there is total — every `CondTest` has a home — because a partial one would mean a rule made in a from-scratch workbook silently not being saved.
- **One button, not a dialog.** "Highlight cells greater than N" is the rule people reach for first and has exactly one parameter. The engine takes text, blank, duplicate and formula rules too; those need a real editor, and half a dialog would be worse than a prompt.

## E1/E2 — The environment and its graders

- **The environment is a new crate, not a mode of the engine.** `crates/env` depends on `engine` and `engine` knows nothing about it. Training-loop concerns — snapshots, observations, step budgets, graders — have no business in the library the spreadsheet itself runs on, and the day one of them needs a shortcut through the model is the day the single mutation path stops being single.
- **`step` takes an `engine::Action`, the same type the toolbar dispatches.** Not a natural-language request and not a bespoke "agent action" enum. Whatever turns intent into actions is a layer above, where it can be evaluated separately from the layer that decides whether it worked — and the environment inherits every invariant the action path already has, including undo and replay.
- **A snapshot is the hash of its canonical bytes.** Ten thousand generated variants of one task share one stored workbook, so a dataset stays a file somebody can read. The canonicalization sorts every object key recursively, because a hash that depended on map iteration order would give the same workbook a different id on every run and every trajectory recorded yesterday would point at nothing today.
- **`Sheet::cells` and `Sheet::formats` now serialize keyed by A1.** JSON map keys must be strings and `CellAddr` is a struct, so a workbook simply could not be written as JSON before this. Nothing serialized `Workbook` directly, so no format was broken. The side benefit is that a stored snapshot reads as `"B7": {...}`, and a snapshot is the unit a dataset gets debugged in.
- **Loading a snapshot recalculates it.** Cached values, spilled blocks and conditional formats are all derived; a snapshot that carried them could disagree with what the engine would compute. Recomputing on the way in is what makes `reset` mean *this exact starting state* even for a file an older build wrote. The history is cleared too — a reset is a starting point, not an edit.
- **An observation is a summary with a fixed budget, and says where it truncated.** Errors, changed cells and formula shapes each have a cap and each report the real total beside the capped list. A policy that cannot tell "these are all the errors" from "these are the first 32" will confidently believe it finished.
- **Formula shapes are R1C1, and getting this wrong was the sharpest bug of the session.** The first implementation normalized a formula by shifting it to the origin with `refs::offset` — which correctly returns `#REF!` for a cell three columns left of column A. Every formula reading up and to the left therefore normalized to the same string. In an observation that merges unrelated formulas into one group; in the grader, which shares the function, it meant `CellFormula { expect: "=B3*C3" }` *passed* on a cell holding `=A3+B3`. `R[0]C[-2]` has no floor. Absolute references keep their absolute spelling, which is right: a column filled with `$A$1` really does have one shape.
- **A grader reads the workbook, never an observation.** If the summary is wrong the policy is misled and scores worse; the score stays correct. Any other arrangement lets a summarization bug silently inflate results, which is the one failure mode an evaluation harness cannot survive.
- **Grading a value falls back to the engine's fifteen-digit rule, not to exact equality.** `0.1 + 0.2` is `0.30000000000000004`, and a grader that failed a correct column of sums over the last bit would be teaching a policy to avoid correct answers. An explicit `tolerance` still wins when the task sets one, because "within a penny" is a real requirement only the task knows about.
- **`RangeFilled` compares shapes, so it catches the two ways of faking a fill.** Pasted literals hold no formula; `=B2*C2` repeated in every row holds one but does not shift. Grading on values alone accepts the first, and grading on text accepts the second.
- **Every grade reports `incidental_changes` whether or not it passed.** A policy that completes more tasks while quietly rewriting cells nobody asked about is *worse* than one that completes fewer, and average reward cannot see that. `Unchanged { ranges }` is the hard version for cells a task can name in advance; the incidental count is the soft one for everything else. It counted honest work as collateral until the check addresses were resolved against the default sheet the same way the graders resolve them — an unqualified `D2` was being stored against sheet `""` while the diff reported `Sheet1`.
- **A rejected action still costs a step.** A policy that could propose illegal edits for free would be scored as if flailing were costless, and "how many steps did this take" would stop being comparable across policies. The refusal is a `StepResult` with `applied: false` and the engine's own complaint, not an error that ends the episode: an agent proposing something illegal is ordinary, and it is something to learn from.
- **Per-step changed cells come from the events; the exact diff is a separate, slower call.** Diffing two workbooks on every step would make `observe` the slowest thing in the loop. The events are the engine's own account of what it did — including the `Recalced` list, so a policy can see that editing `B2` moved `D2`. Range-shaped events (a sort, a fill) report their region rather than each cell, and `Env::diff_from_start` is there when an exact answer is needed.
- **Selection is environment state, not workbook state.** It is not in the snapshot and does not move the hash, so two runs that scrolled differently are not two states and deduplication keeps working. It is still recorded, because a trajectory without "the range I was working on" is unreadable afterwards.
- **`Env` is deliberately not `Clone`.** Branching an episode goes through the snapshot store — `checkpoint()` then `reset()` — so a branch is a thing with an id that a trajectory can name, rather than an anonymous copy in somebody's memory.
- **The CLI builds a starting workbook by replaying an action log.** A serialized `Workbook` carries parsed formula ASTs and is nobody's idea of an input format; an action log is what the capture pipeline already writes and what a person can write by hand. It is also the same path the determinism tests exercise, so a starting workbook built this way is reproducible by construction.

## E3/E4 — Trajectories, and turning one demonstration into many

- **A trajectory must replay, and everything else in the format follows from that.** Given its `initial_snapshot` and its actions, running them again has to reproduce every per-step state hash. That is what makes a recorded demonstration a fact rather than a claim, and it is checked per step rather than only at the end, because two different sequences can arrive at the same workbook and only one of them is what was recorded. `gridline-env validate` runs it over a whole dataset and is in `make ci`.
- **The workbook is never inline.** Starting and ending states are stored by hash. A test asserts it — `a_trajectory_does_not_carry_the_workbook_inline` — because size discipline that is only hoped for is size discipline that erodes.
- **Observations are recorded but nothing reads them back.** They are the input side of a training example, so they are kept; replay ignores them entirely, so changing the summarizer invalidates no trajectory. A recording policy chooses how many to keep, because a full observation per step is the largest thing in the file and a replay-validation run does not need any.
- **A refused step is kept, not dropped.** What a policy tried and could not do is the most informative thing in the record, and dropping it would make the step count a lie. Replay checks that a refusal replays *as* a refusal.
- **Termination is recorded, not inferred.** "Ran out of steps" and "decided it was done" produce the same final state surprisingly often and mean completely different things about the policy. An abandoned episode is not a demonstration even when the grader passes it: its last state is where somebody stopped, not the answer.
- **The final diff separates formulas from values.** Replacing `=B2*C2` with the literal `10` changes nothing you can see and everything that matters.
- **Every perturbation is engine actions plus an address remap, never a direct edit of the model.** Inserting two rows is `Action::RowInsert`, so every formula in the workbook is rewritten by the same reference-rewriting code copy, paste and fill go through. A second implementation of "what happens to a reference when a row appears above it" is how generated data comes to disagree with the product. It also meant exposing `refs::map_refs` — better than exposing a fourth special-purpose function, and much better than the generator growing its own expression walker that would drift.
- **The generator is heuristic and the gate is what makes that safe.** Extending a filled column when rows are appended is a guess about what the demonstration meant. A variant is replayed and graded and kept only if it passes; rejections are returned with the grader's own reason rather than swallowed, because a recipe that never survives is a bug in the generator and quietly producing fewer variants is how nobody finds out.
- **The gate has caught real bugs, which is the argument for it.** `CellFormula`'s `expect` is a formula written as it would appear at `at`, and the first implementation moved the address without moving the formula — so every variant of a task with a total row was rejected, and a rejection that comes from the generator rather than from the perturbation is invisible from the outside. It also caught a wrong expected total in a task spec written by hand.
- **`append_rows` does not move what sat below the data, and that is recorded rather than fixed.** Telling "a footer under the table" from "an empty cell inside it" is the same guess table detection makes, and guessing wrong would silently relocate an output. A demonstration with a grand-total row is rejected rather than mangled, which is the outcome to prefer — and it is why `make dataset` reports three rejections and should.
- **A perturbation that changes the inputs changes the right answer, so value expectations are recomputed from the replayed demonstration.** Those checks stop being independent evidence — the demonstration is being trusted, which is why only a *validated* one is ever augmented — and a variant left with nothing but recomputed expectations is refused as proving nothing. The structural checks are what still have teeth.
- **The dataset is JSONL, one object per line, with no enclosing array.** A dataset that has to be parsed whole before its first record can be read is a dataset nobody streams, and an interrupted write of a JSON array leaves a file that will not parse at all, where an interrupted JSONL write loses one line.
- **`record` drops a demonstration that fails its own grader.** A failed recording is a real thing worth keeping — it is the correction loop's raw material — but it does not belong in a file called a dataset of demonstrations, so it is reported and dropped rather than silently mixed in.

## A1–A5 — The agent

- **A planner decides what, a compiler decides where, and nothing else is allowed.** `plan::Step` has no `RunCode`, no `Eval`, no `ClickAt`. A plan can therefore be read before it runs, survives the sheet moving because nothing in it is an address, and fails attributably to one half or the other. The cost is stated rather than hidden: a planner can only say what the enum can express, and anything else has to be added there first with a compiler and a validator to match.
- **`export_workbook` compiles to no actions and exists anyway.** Finishing is something the planner *declares*, not something inferred from it running out of ideas — which is the difference between `Termination::Done` and `Termination::BudgetExhausted`, and they mean different things about the policy.
- **A placeholder means this row's cell inside the table and the whole column outside it.** One syntax covers "each row times its price" and "the total of the column", and the rule is decided by where the formula lands rather than by a second spelling nobody would remember.
- **Header matching is loose about case, spacing and punctuation and nothing else.** Matching `"Price"` to `"Unit Price"` would make a two-price table resolve to whichever came first, and being wrong about which column is the price is the exact quiet error the whole design is arranged to avoid. A header that is not there is an error naming the ones that are.
- **Four layers before anything is committed, and the third is the one that earns its keep.** Compile catches a missing column; validate catches scope, structure, bad references and blast radius; *rehearsing on a clone* catches what neither can see — a step that changes nothing, a formula that parses and validates and evaluates to `#VALUE!`, an effect landing outside the declared range by a route the action list did not show. Only then does the real environment see it.
- **A failure becomes feedback, not a retry.** The planner is told what went wrong in the words a person would be given — "there is no column headed `Quantity`; the ones here are `Item`, `Qty`, `Price`" — and steps after a failed one are abandoned, because they were written assuming it succeeded and running them anyway is how an agent digs a hole.
- **`Recorder::env_mut` was a hole in the recording and had to go.** The execution loop committed its actions through it, which meant they never reached the trajectory: the record came out empty and replayed *perfectly*, because there was nothing to check. The recorder now exposes `checkpoint`, `set_selection` and `set_active_sheet` and nothing that can step. A test asserts a run that did work recorded steps.
- **The validator's cell limit counts recalculation.** Editing one input that four hundred formulas read is a four-hundred-cell change, and an agent allowed to make it because "it only wrote one cell" has been measured by the wrong number.
- **Replacing a formula with a literal is refused by default.** It is what a policy does when it computes the answer itself instead of writing the formula: every value-based check passes, the column stops updating, and nobody finds out until the inputs change.
- **`allow_sheet_changes` is separate from `allow_structural`.** Deleting a sheet is the most destructive thing in the vocabulary; enabling row inserts must not quietly enable it too.
- **The rule planner infers operands from column types when the instruction names none, and says it is guessing.** "The total is the quantity multiplied by the price" over headers `Qty` and `Price` names no columns this table has. The types still say which two could be meant, so a plan is offered at a confidence low enough that any router sends it somewhere better. It refuses to guess the order of a subtraction, because `{a}-{b}` and `{b}-{a}` are different answers. It also refuses to let the output column be one of its own inputs — without that, the same sentence resolved its left operand to `Total` and proposed a column that reads itself.
- **The router escalates on the first refusal, and that rule matters more than the confidence threshold.** A cheap policy allowed to retry after being refused proposes variations of the same mistake until the budget is gone, looks busy, and produces nothing.
- **Only clean successes become habits.** A plan that passed while touching cells nobody asked about is not remembered: promoting it turns one careless success into a policy that is careless every time.
- **A micro-policy says how it bound each slot.** By a header name seen before is nearly a fact; by "it is the only numeric column left" is a guess, and the confidence differs by enough that a router treats them differently. A memory that could not tell them apart would be a fast way to be wrong.
- **Measured, not asserted: memory makes the second pass cheaper at the same score.** Over the generated corpus, pass one is 7/11 with 15 planner calls and 4 replans; pass two is 7/11 with zero of either, every proposal answered by one distilled policy with support 7. A test asserts the score does not drop, because cheaper *and worse* is a regression with a budget line.
- **Two limitations left visible rather than papered over.** The rule planner does not solve the two-step "fill a column then total it underneath" tasks and fails all four variants of them — that gap is the shape of what a model planner is for, and teaching the rule planner one more sentence would hide it. And a micro-policy can declare a task done that it only partly solved: nothing in the loop catches that, because nothing was refused, and only the grader notices afterwards.
- **Two corpus bugs the agent found that the gate could not.** A column insert with no fill leaves a *blank* column, table detection quite correctly stops at it, and the variant becomes a narrower table rather than one with something irrelevant in the middle — the demonstration replay passed it either way, because fixed addresses do not care where the table ends. And each variant's step budget was set to exactly the demonstration's action count, so an agent that writes a column header before the column ran out on the last row of a task it had solved. A budget is meant to stop a runaway loop, not to fit like a glove.

## C1–C4 — Corrections, evaluation, promotion

- **A divergence is computed from state hashes, not from actions.** Two different action sequences can reach the same workbook, and the point worth learning from is the first place the *states* differ — not the first place the keystrokes did.
- **A repair on top of the agent's output is recognised as one rather than inferred.** It is the commonest correction in practice: the user does not undo, they fix what is there. Both runs then agree through the whole attempt, which is accurate, and the record says so explicitly instead of leaving a reader to work it out from a number that happens to equal the attempt's length.
- **A repair is only a correction if it worked.** A user who undid the agent and then did something equally wrong is not a teacher, and training on it would be worse than ignoring the episode. The grader decides; ungraded is not clean either.
- **A preference pair is anchored at the diverging state, not at the start.** The two sides agreed up to that point, and a preference over a shared prefix is a preference about nothing.
- **Every preference carries the grader's reason.** An unauditable preference is how a dataset acquires somebody's bad afternoon as a training signal.
- **The correction log reports what it could not use.** A capture pipeline that silently discards most of what it sees looks exactly like one that is working.
- **A corpus version is the hash of its contents.** A version somebody has to remember to bump is a version that stops being bumped, and then two incomparable scorecards compare fine.
- **An evaluation opens the corpus read-only.** Every committed step checkpoints, so scoring against a directory-backed corpus left a trail of new snapshot files in it — and a corpus that changes when you measure against it is not a corpus, it is a moving target.
- **Promotion is a list of conditions, not a comparison of numbers.** More runs touching cells nobody asked about, more forbidden-cell violations, fewer tasks solved, any origin's pass count down, or *any task that used to pass now failing* — each holds the release on its own. That last one is the regression an aggregate cannot show: one task lost, two won, net positive, somebody's Monday broken. Every reason is reported, because blocked for three reasons and fixed for one is still blocked.
- **A candidate identical on every dimension is held rather than shipped.** A release nobody can point at a reason for is a release nobody can roll back with a reason either.
- **Wall clock is recorded and cannot gate anything.** A release rule that depends on how busy the machine was is not a rule. A test asserts that two candidates differing only in elapsed time get the same verdict.
- **A resumed run inherits neither the plan nor the trajectory.** The planner is asked afresh, because a plan is intent formed from an observation and the observation has moved on. The trajectory restarts from the checkpoint, because stitching two recordings together produces state hashes that are real and an action list that never happened in one sitting — and it would not replay.
- **The resume path lost the task's step budget and every unit test stayed green.** `Recorder::start` resets the environment through the general `reset`, which puts the budget back to the default; on a task whose data is two hundred rows long the run was cut off partway and it looked like the policy giving up. The only thing that noticed was the corpus score, three commits later. `Recorder::start_task_at` and `Env::reset_for_at` exist so the start snapshot and the budget can differ, and a test now pins it.
- **A task that says "Qty times Price" and checks only `RangeFilled` is under-specified**, and the agent finds that out before anybody else does: `=Qty+Price` filled down satisfies a shape check perfectly. Found by writing a deliberately wrong planner and watching it pass.
- **Two things are honestly not built.** Nothing in the product fires a correction capture — the record format, the divergence and the distillation are done and tested end to end against the real agent, but the UI hooks that would notice a user undoing the agent are not. And nothing here trains anything: this produces supervised examples and preference pairs in a documented format and stops there.

## Editing and selection, held to Excel

- **A press on the grid commits the edit before it does anything else.** The editor used to stay open while the selection moved underneath it, which is why the app felt broken rather than unfinished: the cell you clicked never looked selected, dragging a range appeared to do nothing, and Delete went into the floating input instead of clearing the cells you had just highlighted. One line at the top of `handleMouseDown`, and three of the reported symptoms are the same bug.
- **Blur commits too, and the formula bar is the one exception.** Anything that takes focus — a toolbar button, a panel, another app — has to land the value, or it vanishes with the editor and the user is looking at a cell they thought they had just filled. Moving into the formula bar is continuing the same edit rather than abandoning it, and the two inputs share one `editing` state, so committing there would tear down what the formula bar is about to type into. It is keyed off `relatedTarget` being inside `.formula-bar`, which is a real coupling and is cheaper than the alternative of a shared focus-owner state machine.
- **Commit is idempotent, because two paths reach it.** A grid press commits explicitly *and* blurs the input, which commits again. `commitEdit` clears `editingRef` before it applies, so the second call is a no-op; without that the cell would be written twice and the event log would carry an edit that never happened.
- **`cancelEdit` clears the ref immediately, not at the next render.** Escape unmounts the editor, which blurs it, which commits — so leaving the discarded value in the ref for one tick would save exactly what the user pressed Escape to throw away.
- **Enter mode and edit mode, distinguished by how the edit started.** Typing over a cell means the arrows commit and move, which is what lets a row be filled by typing and arrowing without ever reaching for Enter; F2 or a double-click means the arrows belong to the caret, because the point of opening an existing value is to amend it. The flag was already in `EditState` as `replacing` and only the arrow handling was missing.
- **A half-typed formula stays on the caret in both modes.** Excel would enter pointing mode and let the arrows pick the next operand. Until that exists, moving the caret is the harmless reading of the keystroke; committing would turn `=A1+` into an error the user never asked for. This is a deliberate gap, not an oversight.
- **The dev script keys wasm freshness off `pkg/package.json`, not the `.wasm` blob.** wasm-pack writes the manifest last, so a build that dies partway — the wasm-opt download failing behind a proxy, which is what happened here — leaves the blob without it. `gridline-wasm` is a `file:` dependency, so npm's symlink then points at a directory Vite cannot resolve as a package, and every module that imports the engine 500s. Keying off the blob called that wreckage fresh and would have served it forever, since nothing in the sources is newer than it. The blank page had two causes, and fixing the first one hid the second.

## Pointing, completion, and General as a width-dependent format

- **A press on the grid means "point here" when the formula is mid-expression, and "commit and go there" otherwise.** The two readings of the same gesture are told apart from the text alone: `pointingSlot` answers whether a reference may go in at the caret. `=AVERAGE(` captures the drag; `=SUM(A1:A3)` does not, which is what keeps "click somewhere else to finish" working. The previous commit made this worse before it made it better — committing on every press turned `=AVERAGE(` plus a drag into a parse error, which is exactly the report that came back.
- **`preventDefault` on the pointing press is load-bearing.** Without it the press blurs the editor, blur commits, and the half-written formula is gone before the drag begins. It is also why pointing needs no special case in the blur handler.
- **A drag rewrites one span rather than appending per mouse move.** `pointAt` returns the slot the next point should use, widened to cover what it just wrote. The first version returned nothing and `=AVERAGE(` grew into `=AVERAGE(A1:A3A1:A2A1` — the failure is silent in a click and obvious in a drag, which is why the drag test came first.
- **The caret is restored in a layout effect, not left to React.** A controlled input puts the caret at the end when its value is replaced from outside, so pointing into `=SUM()` would leave the user typing after the bracket rather than inside it. The same fix covers accepting a completion.
- **Pointing works from the formula bar because the two inputs share one `editing` state.** The element to write into is found from `document.activeElement`, which is a real coupling to a class name and is still cheaper than a focus-owner state machine for two inputs.
- **The function list comes from the engine; the descriptions do not.** `functionNames()` reads the same `IMPLEMENTED` a Rust test pins to the dispatcher, so the menu cannot offer a function that does not exist. What the engine does not carry is what each function is *for*, and modelling arguments in Rust to render a tooltip would be a large change for a small purpose — so `function-help.ts` owns the prose and a web test fails if the two lists disagree in either direction. A function with no entry still completes; it completes bare.
- **The menu waits for two letters where Excel opens on one.** `=A` is far more often the start of a reference than of a function name, and the menu drops over exactly the cells about to be pointed at — so opening on one letter would put ABS, AND and AVERAGE on top of column A every time somebody typed `=A1+A2`. Two letters costs almost nothing and keeps completion and pointing out of each other's way.
- **Escape closes the menu and nothing else.** Dismissing a menu is a reflex, and a reflex that also throws away the formula behind it loses work. The second press cancels the edit.
- **General is not a fixed format, so how many decimals a cell shows is a question about the column.** The engine prints 15 significant digits because that is the answer; only the renderer knows the column is 100px wide. `=AVERAGE(A1:A3)` over 1, 3 and 4 rendered as `###########` because 2.66666666666667 is sixteen characters — hashes are meant to say "this column is too narrow for this number", and a number a user would happily read as 2.666667 does not deserve them. A cell with an *explicit* number format is left to hash: somebody asked for those digits, and quietly showing fewer would be a lie about what the cell says.
- **Pointing by arrow key is still not built.** Excel lets the arrows pick the operand once a formula expects one; here they stay on the caret. Building it means tracking a pointing cursor that is not the selection, and the mouse gesture is the one that was reported and the one people reach for. Recorded rather than half-done.

## Arrow pointing, and whole-column references

- **Arrow pointing is enter-mode only, and one caret-arrow ends it for the whole edit.** Excel's rule, and it is stickier than it looks: an arrow that lands where no reference is expected does not merely move the caret, it drops the edit from enter mode into edit mode, so every later arrow belongs to the caret too — even one that stops after an operator. Without that, going back to fix `=1+2` starts pointing halfway through and the fix becomes impossible to type. An edit opened with F2 starts in that state, because opening an existing value is amending it.
- **Bare modifier keydowns are not input.** A run of arrows picking a reference is ended by any other keystroke, and Shift arrives as its own keydown — so the rule as first written ended the run on the exact gesture it existed for, and `Shift+Arrow` re-pointed the anchor instead of widening the range. Caught by a test that asserted narrowing works too, which is what distinguishes "the anchor is held" from "the anchor happens to be where I left it".
- **Pointing carries the value it produced, not just the span it wrote.** Several points can land between two renders — a fast drag, a held arrow — and `editing.value` only catches up on re-render. Splicing into it would undo the point before last. The drag showed this immediately (`=AVERAGE(A1:A3A1:A2A1`); the arrow path would have shown it only under key repeat, which is exactly the kind of bug that ships.
- **Pointing at a column header needed the engine to learn `A:A` first.** It was recorded as a UI gap and was not one: the parser rejected whole-column references outright, so the gesture could only ever have produced a formula the engine refused. Writing `A1:A1000` instead would have been the wrong shape — a reference that stops growing is the thing `A:A` exists to avoid.
- **`RangeSpan` marks which axes a range actually named.** `A:C` is a rectangle like any other; the difference is that one axis came from the sheet rather than the author, and that shows up in exactly three places — printing it back (`A:C`, not `A1:C1048576`), rewriting it on a structural edit (an axis nobody wrote cannot shift, and shifting it would push the bottom off the grid and produce `#REF!`), and evaluating it.
- **Evaluation narrows an open axis to the used range; dependencies do not.** Narrowing is what makes `SUM(A:A)` cost the same as `SUM(A1:A10)` instead of building a million-element vector per formula. Keeping the *dependency* on the whole column is what makes filling A50 recalculate it — and that is the only reason anybody writes `A:A` rather than `A1:A100`. Getting this backwards would produce a fast implementation that silently stops updating.
- **Narrowing is visible to the functions that count absence, and that is recorded rather than smoothed over.** `COUNTBLANK(A:A)` answers 0 where Excel answers 1,048,573, and `ROWS(A:A)` answers the used height. Both are in PARITY.md as recorded differences, and both cost the score: 99.1% to 98.5%. Fixing them means teaching each counting function that its range may be open, which is the right answer and is not free.
- **A formula inside the band it reads is circular, and the dependency graph sees it.** `=SUM(A:A)` written in column A, or `=SUM(1:2)` written in row 2, answers `#CIRC!`. Worth stating because it is the one place the unclamped dependency and the clamped evaluation could have disagreed — the narrowed range would not have contained the cell.
- **R1C1 shapes omit the axis the reference did not name.** Both the miner and the environment's observation build shapes this way. Spelling out `R[-3]C[0]:R[1048572]C[0]` would make `=SUM(A:A)` a different shape in every row it appears in, which is the one thing R1C1 exists to prevent — the miner would stop seeing it as a habit and the environment would grade a correct formula as the wrong one.
- **`RangeSpan::Cells` is skipped when serializing, and the dataset check is why.** Snapshots are content-addressed over canonical JSON of the workbook and the AST is in there, so writing `"span":"cells"` on every ordinary range changed the hash of every workbook containing one — `1/2 trajectories still replay`. Omitting the default keeps a workbook with no open ranges byte-identical to what it was before the field existed, which is what a refinement ought to be. A test pins the serialized shape, because the next person to add a field to the AST will not think of this either.

## A capture pipeline that lied about working

- **The bug was three lines of shell, and the reason it survived was a missing number in the UI.** `dev.sh` guarded the token seed with `[ ! -f .dev-token ]`, but the redirection `> .dev-token` creates the file *before* the command runs — so a run that died at that step (the two-binary ambiguity, fixed weeks earlier) left an empty file the guard would never replace. The web app then sent `Authorization: Bearer ` on every request, the server answered 401, and 401 is not retryable, so the queue discarded each batch. The chip read "capturing", the transparency page read "0 events waiting to send", and the database stayed empty. Every individual component behaved exactly as designed.
- **`discarded` was tracked and never shown, which is the same as not tracking it.** The queue has counted permanently-rejected envelopes since M4 — there is a test for it — but nothing rendered the number. A count that exists only in a unit test is not observability. It is now on the chip and stated in words on the transparency page, and a rejection overrides the nominal state: the chip says "not recording" rather than "capturing", because "capturing" while every batch is refused is precisely the lie that page exists to prevent.
- **Pending and rejected are different problems and are shown differently.** A backlog drains when the server comes back; a rejection never will. Collapsing them into one "not delivered" number would have made the healthy case (a laptop offline for a minute) and the broken case (a bad token) look identical.
- **The guard now tests for a non-empty token and writes through a temporary file.** A failed seed leaves nothing rather than a booby trap, and the script exits loudly instead of starting an app that cannot record anything.
- **Found by a user asking "how do I see what was captured?"** — the honest answer at the time was "query the database", which is why nobody had noticed the app had been silently dropping events. The question was better than the feature.
- **The transparency page now shows what was captured, not only what would be.** `GET /v1/events/recent` returns the caller's own events and is deliberately not admin-gated — it is their record. It shares the row-to-envelope conversion with the export, so the page cannot describe one thing while the database holds another, and it is consent-gated by the same clause: revoking hides what was already collected, because a history you can still read afterwards is a weaker promise than the notice makes.
- **The payload is rendered, not re-described.** A structural-mode literal arrives as `{hash, len, type}` and is shown as `⟨number:5 4c415dc4…⟩`. Explaining the redaction in prose is a claim; showing the user the thing that replaced their number is the demonstration — and it sits directly above the paragraph that makes the claim.
- **An unreachable server is reported rather than rendered as an empty list.** "Nothing captured" and "cannot ask" look identical and mean opposite things, and conflating them is how the silent-drop bug survived in the first place.
- **A token the server rejects is dead, and "the stored one wins" must not mean "wins forever".** The dev token was adopted only when nothing was stored, which is right — a hand-typed token should beat one baked into the environment. But it made re-seeding a development database unrecoverable: the browser kept presenting a token the new database had never heard of, and no reload, restart or further re-seed replaced it. Every event was rejected and discarded on a machine whose setup looked correct, and the *fix* for the previous bug — `rm .dev-token && make dev` — actively caused it, because seeding mints a new user. A 401 now swaps in the dev token and retries exactly once; production builds have no dev token, so nothing changes there.
- **Exactly one retry, and only when the credentials actually changed.** A recovery hook that always claims to have changed something turns a server rejecting everything into an infinite request loop. The hook returns false when it has nothing better to offer, and the retry flag is passed down rather than kept in module state, so concurrent requests cannot borrow each other's attempt.
- **The grid specs stopped clicking through the consent modal.** They opened the app and clicked *Decline*, which quietly made them depend on a database they do not control: the modal only appears when the server has no consent on file, so the suite passed on a fresh checkout and hung thirty seconds a test on any machine where somebody had answered the notice once. Green in CI, red for the developer — the worst way round, and it is how a suite stops being believed. `e2e/support.ts` answers the notice in `localStorage` before the app boots. `capture.spec.ts` still drives the real modal, because there the modal is the subject.

## Publishing it

- **The published build has no backend, and that is a decision about consent rather than about hosting.** The app is static — the engine is wasm, so the entire spreadsheet works with no server — and the only parts that need one are capture, the consent notice, the transparency page and mined routines. Shipping those to a public URL would mean recording what visitors type, and offering them a consent notice whose answer nothing could act on: a notice that asks for a decision and then ignores it is worse than no notice. `VITE_STANDALONE=1` removes all four, and an end-to-end test drives the *built bundle* and fails if it makes a single request to the API, because the flag is inlined at build time and only the artefact can show what was inlined.
- **Not Replit.** It would have to build Rust to wasm on every cold start — a release engine build plus `wasm-pack`, on a container that sleeps — and the alternative is uploading a `dist/` built elsewhere, at which point it is a slower static host. The repo is already on GitHub, so Pages needs no new account and no build of its own.
- **`base` comes from the environment, not the config.** A project site is served from `/<repo>/` and a self-hosted copy from `/`; hard-coding either breaks the other. `VITE_BASE` defaults to `/`, so every existing build — dev, `make ci`, a domain root — is unchanged, and only the Pages workflow sets it.
- **The stock Jekyll workflow is removed rather than left alongside.** GitHub's "Deploy Jekyll with GitHub Pages dependencies preinstalled" template was added through the web UI while looking for a way to publish the app. It builds `source: ./` with `jekyll-build-pages`, so what it would publish is the repository's markdown — README, PROGRESS, this file — rendered as a blog, at the URL meant for the spreadsheet. It also takes the `pages` concurrency group with `cancel-in-progress: false`, so whichever of the two workflows started first would hold the group and the other would queue behind it: the published site would be whichever won the race on that push. Two workflows deploying to one Pages environment is not redundancy, it is a coin toss.
